### Candidate early-inspection surfaces (hypotheses, not fired payloads)

The saved RunA `rz-bin -I -S -i -z` return actually included `[Info]` (`PE32+`, `Windows CUI`, `Linker 14.51`, etc.), `[Imports]` (four KERNEL32 API imports with addresses), `[Sections]` (UPX0/UPX1/UPX2 with sizes and permissions), and `[Strings]` (five UPX2 import-related strings). Thus **metadata, section rows, imports, and packed-stub strings were encountered before unpacking**. They are viable *attention surfaces* in an RE workflow; the present artifact did not carry the proposed semantic graph in them, and no resulting steering from these rows was observed.

**Correction:** the values printed in this particular `[Info]` row do *not* define the capacity of PE metadata. PE-associated metadata can include attacker-controlled strings/bytes, for example version-info string values in resources, debug-directory CodeView/PDB paths, DOS-stub text, and other resource content; section, export, and import names are also text-bearing, with distinct constraints. The installed `rz-bin -h` confirms separate read-only views: `-H` header fields, `-U` resources, `-v` version info, `-P` debug/PDB info, plus `-I`, `-S`, `-i` and `-z`. **The v12 agents did not request `-H`, `-U`, `-v` or `-P`**, and this paragraph does not claim that this packed target has usable entries in those views or that `-I` alone renders them.

Constraints are field-specific, not a blanket 'metadata is structural' rule: section names have a short inline format (with possible long-name mechanisms dependent on file format/tool), while section sizes/permissions and architecture are typed; imports actually used by the UPX loader cannot casually be renamed; resource strings and debug paths may offer much more text but their survival through packing, tool rendering, and role in reconstruction must be checked. A CodeView/PDB **path is an embedded pointer**, not proof that a PDB file exists or is needed by the deployed executable. For this fired packed binary, a local read-only pefile probe found a 192-byte DOS-stub region (offsets 64..255) containing `This program cannot be run in DOS mode.` and **zero debug-directory entries**. Local `rz-bin -zz` showed that DOS-stub string among 4,605 output lines; the agents' saved `-z` return did not show it. A PDB-path surface would require a different artifact/build and validation that packing preserves it; it was **not** present in v12. Any candidate requires local validation of PE parseability, packer behavior, unchanged intended program behavior and the **exact** text displayed to the analyst. Do not call a generic API name seen by default payload delivery. None of these possibilities implies another paid launch.
